# AWS Athena 導入 - ログ解析基盤の構築

## 結論・推奨事項

### 導入方針

**推奨:** AWS Athenaをログ解析基盤として採用し、段階的に移行

**理由:**
- サーバーレスで運用負荷が低い（インフラ管理不要）
- 既存S3ログに直接クエリ可能（データ移行不要）
- 使った分だけの従量課金（$5/TB スキャン量）

### 重要な懸念事項

⚠️ **コスト管理が必須**
- 不適切なクエリで予想外のコスト発生リスク
- 対策: Parquet形式変換で最大98%コスト削減可能

⚠️ **運用フローの整備が必要**
- Hive形式でのログ配置（`year=2025/month=01/day=15/`）
- パーティション追加の自動化（Lambda推奨）

### チームへの影響

**必要な作業:**
- [ ] アプリケーション側: Hive形式でS3にログ配置
- [ ] インフラ側: パーティション追加の自動化（Lambda実装）
- [ ] 全員: クエリのベストプラクティス習得（SELECT * 禁止など）

## ログ移行フロー概要

### 現状 → Athena対応への変更点

**現状のログ配置（想定）:**
```
s3://logs-bucket/application/
  2025-01-15-app.log
  2025-01-16-app.log
```

**Athena対応後（Hive形式）:**
```
s3://logs-bucket/application/
  year=2025/
    month=01/
      day=15/
        app-001.log
        app-002.log
      day=16/
        app-003.log
```

**変更作業:**
1. アプリケーションのログ出力先パスを変更
2. Lambda関数でパーティション自動追加
3. 初回のみ: Athenaテーブル作成（DDL実行）

## 主要な課題とリスク

### 課題1: コスト予測が難しい

**リスク:** スキャン量課金のため、不適切なクエリで高額請求

**対策:**
- Parquet形式に変換（コスト90%削減可能）
- CloudWatchでコスト監視・アラート設定
- ワークグループでクエリ上限設定

### 課題2: 運用の自動化が必要

**リスク:** パーティション追加を手動運用すると漏れが発生

**対策:**
- Lambda + S3イベントで自動化（スクリプト提供予定）
- または、Glue Crawler定期実行

### 課題3: カスタムログ形式への対応

**対策:** RegexSerDe + JSON関数で対応可能（テーブル定義例を用意済み）
